## 一、做了什么

1. **接口盘点**：以"首屏加载序列"走查了前端需要的每一个资源——
   auth/csrf → workspaces（current_role）→ projects（current_user_role）→ states（预置五态）
   → issues（过滤/排序/分页）→ comments / activities / labels / tasks / WS 推送。
   **结论：MVP 接口无缺口，不需要新增端点**——前端要的每一块都有契约、有测试、有 schema。
2. **09 契约（接入手册）**：与 00–08 的"接口长什么样"互补，回答"**怎么接、坑在哪**"：
   - 两种开发形态的地址表（runserver 同端口 vs compose 的 8000/8001 分端口）；
   - fetch 封装参考实现（credentials + CSRF 头 + 403 自愈重放）；
   - 错误分流表（400 字段级 / 401 / 403 / 404 防枚举 / 429 / 500 → 各自的前端动作）；
   - 分页语义（越界返回空 results）、查询参数白名单、WS 帧/关闭码/心跳、任务轮询；
   - 十条"常见坑"清单（尾斜杠重定向、跨端口同站、不要按文案分支等）。
3. **docs/API.md** 契约索引补 09 入口。

## 二、为什么这样分工

"方便前端接入"最容易做成"后端多塞几个聚合接口"。这里刻意**不加任何新端点**：
MVP 的接口面已经覆盖前端首屏与交互闭环，多造聚合接口只会制造两份事实来源。
真正的缺口是**操作性知识**（CSRF 自愈、404 别重试、WS 关闭码语义、端口差异），
它们散落在 8 份契约里，前端同学逐份读成本太高——09 把它们收进一份可照抄的手册，
代码示例用无依赖的原生 fetch（框架无关，Next.js/CRA 都能直接落地）。
