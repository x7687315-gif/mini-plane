# 桌面版：关掉界面，整个应用立刻退出（含社区调研）

> 2026-10-04 · 用户要求："关掉界面以后，后台进程直接全部一键删除。"
> 状态：**已修复并通过真机验证（连续两次可复现）**

---

## 一、现象

双击桌面版 → 关掉窗口（点右上角 ×）→ **界面没了，但进程还在**：
`MiniPlane.exe` 残留（甚至累积到 22 个）、8000/3000 端口被占着，
下次双击还会"复用"这一套残留服务。

## 二、我先后试过的两条路，都失败了（有日志为证）

| 尝试 | 结果 | 证据 |
|------|------|------|
| ① 监听 `window.events.closed`，关闭时销毁 Island 窗口 | ❌ 回调**根本没触发** | 日志里没有任何退出记录 |
| ② 后台线程轮询主窗口标题，消失后调 `island_window.destroy()` | ❌ 触发了，但**进程没退** | 日志：`[watch] 主窗口已关闭 → 销毁 Island 窗口并退出应用`，之后无动作、端口仍占用 |

关键测量（不是猜）：
- 主窗口**确实关掉了**（`visible_window_exists()` 返回 False）
- 监视线程**确实触发了**（日志有记录）
- 但 `destroy()` 之后的代码**一行都没执行**

## 三、社区调研（应要求去查）

| 来源 | 结论 |
|------|------|
| **pywebview PR #1844**（官方） | 「GUI 线程重入死锁」：在窗口事件上下文里调用同步 API 会**挂住且 Ctrl-C 都打不断**；该 PR 专门修了这类死锁 |
| **pywebview Discussions #1415**（一模一样的问题："destroy() 了程序却不结束"） | 维护者 r0x0r：destroy 会释放 `start()`，但若还有东西阻塞就不会退出；社区给出的答案是 **`os._exit(0)`** |
| 该讨论的另一条线索 | 程序化 `destroy()` **不会触发** `closed` 事件（所以不能指望它收尾） |

## 四、根因（把现象和社区结论对上）

```
主窗口关闭
   ↓
监视线程调 island_window.destroy()
   ↓
destroy() 阻塞在 GUI 线程上（reentrancy deadlock）
   ↓
后面的 on_quit()（真正停服的那段）永远没机会执行
   ↓
进程与端口全部留在原地
```

**一句话**：我把"停服退出"写在了"销毁窗口"**之后**，而后者会卡住。

## 五、修法

1. **顺序反过来**：`on_quit()` **先**执行；`destroy()` 降级为"没有 on_quit 时才兜底"。
2. **停服不再依赖 pywebview**：`stop_services(procs, hard_exit=True)`
   - 逐个 `kill_tree()`（后端 / 前端）
   - `taskkill /T /F /PID <自己>` —— 杀**以自己为根**的整棵进程树，
     覆盖 pywebview 的 GUI 子进程（它不在 `procs` 里，否则一定会残留）
   - `os._exit(0)` 兜底结束自身

副作用：新增 `window_watch.py`（窗口标题监视，跨进程有效），
`launcher.py` 的 `finally` 与 watchdog 共用同一个 `stop_services()`。

## 六、验证（真机，不是推断）


## 七、过程中的教训

1. **"日志里有触发记录"不等于"动作生效"** —— 这次是看了日志才发现
   `destroy()` 之后一行都没跑，否则我还会继续猜。
2. **改了源码 ≠ exe 里就有**：这轮有两次排查失败是因为打包用的还是旧代码。
   以后改完 desktop 代码，必须先确认 exe 时间戳**晚于**最后一次源码改动。
3. **第三方 GUI 框架的事件/销毁语义要查社区**，不能凭直觉排顺序。
