## 二、三个问题的定性

### ① "没有正确启动" → 设计与心智模型的冲突（可能叠加一个待证实的 bug）

阶段 2 按规格把启动行为改成了**默认隐藏式**：双击后只出现一个 **140×14 的小把手**
贴在屏幕顶边中央，完整面板（520×420、可缩放——用户记忆中"可自由拉尺寸"的那个）
**默认藏起来**，点把手才展开。

一根 14 像素高的细线贴着屏幕边缘，不 hover 几乎不可见 → 用户自然认为"悬浮窗没启动"。
**把手的用途没有任何引导**，这是执行层面对规格 §1.2 的忠实实现，但具体参数（把手过小）
让设计意图落了地却没落到用户眼里。

### ② "尺寸偏小" → 用户看到的是把手，不是面板

面板本身 520×420、`resizable=True`（min 360×96），**没有变小**——只是默认隐藏。
真机探针（pinned 启动）实测面板正常出现（506×382 @ 700,0）。

## 三、今天顺带修掉的一个真问题

用户实测当时的 exe 版本里，点击把手后**无法确认面板是否真的展开了**（那个版本没有
结果日志）。今天用最新 exe 做了两条探针：

- 合成点击（鼠标注入）：**到不了 Python** —— Windows 前台锁，后台进程的注入输入
  打不到应用（`GetForegroundWindow()` 始终是编辑器）。**测试手段限制，不是应用缺陷**；
- `pinned` 配置启动（不经过 show()）：**面板正常出现** ✓ —— 窗口创建/显示路径完好。

结论：面板显示能力没问题；"点击 → show()"这条链有用户实测可证"调用到达"
（`[api] toggle_island` ×2），但**是否成功展开无直接证据**（当时 exe 无结果日志）。
**已加结果日志**（`[island] 面板已展开/已收起`），下次实测一眼可判。

## 四、修改方案（待讨论拍板）

| 方案 | 内容 | 效果 |
|---|---|---|
| **M1 默认首展（推荐）** | 首次启动（从未操作过图钉时）`visibility=expanded`——双击即见完整面板；用户收起/固定后记住偏好，之后按偏好走 | 第一眼就看到"记忆中的悬浮窗"，隐藏式变成用户主动选择 |
| **M2 把手加大** | 140×14 → 约 200×32，"工程 Island"文字**常显**（不只 hover）；位置可选屏幕顶部右侧 | 把手有存在感，不靠运气发现 |
| **M3 面板可拖动（真缺口）** | `easy_drag` 在 Windows 后端是空操作（调研已证实）——无边框面板**现在拖不动**。在面板页眉实现 JS 拖动区（mousedown→桥接→`move_window`） | "操作手感和操作系统"补全的关键一块：能拖、（配合 resizable）能缩放 |
| M4 维持现状 | 不改 | 不推荐：与用户预期冲突已实锤 |

**倾向**：M1 + M2 + M3 一起做（都是小改动），并请用户在下一轮实测里顺手验证
"点把手收起/再展开"（结果日志已就位，一眼可判）。
