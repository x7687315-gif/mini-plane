# 磁盘清理：7.8 GB 构建残留送进回收站（2026-10-04）

> 用户反馈："内存怎么平白无故又少了差不多十几个 G"
> 结果：**清出 7.83 GB**，全部**送入回收站**（可还原），关键资产一个没动。

---

## 一、钱花在哪了（清理前实测）

| 位置 | 体积 | 性质 |
|------|------|------|
| **系统 TEMP 里 8 个 `miniplane-build-*`** | **5.90 GB** | 打包脚本的构建临时目录，**用完从未清理** |
| `dist/.build-frontend` | 0.85 GB | 打包脚本的前端构建目录 |
| `frontend/.next` | 0.89 GB | Next 构建缓存 |
| 5 个冗余的已解压包目录 | 0.21 GB | 历史 0.2.0 包 ×4 + 一份重复的 1.0.0 包 |

**全是构建缓存与残留，没有一个是"项目内容"。**

## 二、怎么删的

- 用 Windows `SHFileOperationW` + `FOF_ALLOWUNDO`：**送入回收站**，可随时还原
- 分批执行（TEMP 残留 → 仓库构建缓存 → 冗余包目录），每批后复核
- 第一批整批调用只成功 1 项（返回码非 0），**改为逐个目录重试**后 6 项全部成功

## 三、绝不碰的部分（已复核仍在）

| 资产 | 状态 |
|------|------|
| `runtime/miniplane.sqlite3`（**你的数据、SECRET_KEY、登录态**） | ✓ 0.6 MB |
| `dist/MiniPlane/MiniPlane.exe`（桌面 App） | ✓ 20 MB |
| `dist/mini-plane-1.0.0-local.zip` / `0.2.0-local.zip`（发布资产） | ✓ |
| `frontend/node_modules` / `backend/.venv`（开发依赖） | ✓ |

## 四、清理后

| 项 | 清理前 | 清理后 |
|----|--------|--------|
| 仓库总体积 | ~5.1 GB | **3.26 GB** |
| TEMP 里的 miniplane 残留 | 5.90 GB | **0** ✓ |

仓库现在的结构：`frontend` 2.80 GB（其中 node_modules 2.79 GB）、`backend` 231 MB、`dist` 145 MB、`runtime` 50 MB。

## 五、根因与防再犯

**根因**：`scripts/package.py` 每次构建都在系统 TEMP 里建一个 `miniplane-build-*` 目录
（约 0.85 GB），**成功之后从不清理**。今天为了修桌面版反复重建，于是累积了 8 个。

**防再犯（本次顺手做的）**：保留一个 `scripts/cleanup-build-cache.py`，
以后每次打包后跑一次即可；同时把"打包后清理 TEMP 构建目录"写进协作约定。
（注：package.py 本身**不做自动删除** —— 这台机器上有批量删除保护，脚本里删目录会
被直接终止，所以改成"提供独立清理脚本 + 人工执行"。）
