# Mini Plane「个人工程优先」UI 重构探讨指令

> **本指令取代上一版《Mini Plane UI 重构设计探讨指令》。** 本轮的产品立场已经明确：Mini Plane 主要服务于一个人持续推进多个工程；团队协作是附加能力，不再与个人使用平衡分配首页、导航和默认操作的注意力。
>
> **本轮只做产品体验与 UI 设计探讨，不改生产代码、不执行全仓库 Bug 审计。** 先交付可比较的结构方案和低保真原型，等待用户评审后再安排实现。

---

## 一、你的角色与本轮目标

请以资深个人效率产品设计师、交互设计师的身份，研究 Mini Plane 当前真实界面，提出一套以**个人工程推进**为中心的 UI 重构方案。

不要把任务理解为“将个人模式和团队模式做得一样完善”，也不要把它理解成单纯的视觉翻新。请重新回答：一个人每天打开 Mini Plane，是为了什么？软件应该如何让这个人更快知道进度、继续工作、记录结果，并在需要时管理多个工程？

本轮目标按重要性排序：

1. **个人使用路径优先**：用户无需先理解 Workspace、成员、角色等协作概念，就能创建工程、推进任务和记录进展。
2. **减少重复流程**：减少重复填写、反复跳转、来回滚动、重复打开相同设置，以及为完成一个简单动作而经过的多层 UI。
3. **降低首屏认知负担**：首页能快速回答“我的工程到了哪、现在最值得继续什么”；工程页能让人直接进入工作，而不是先处理一堆管理控件。
4. **保留产品差异**：Task 表示计划做什么；Worklog 记录实际做了什么、结论、阻塞与下一步；Stage 描述较长周期路线；NOW/NEXT 表示当前推进重点；Agent 状态必须来自真实上报。
5. **保留品牌并提高可读性**：延续 Blueprint Editorial（蓝图编辑风），但不把网格、装饰标签和极小字号当作不可调整的教条。
6. **为后续工程实施准备设计依据**：给出页面结构、关键流程、原型、取舍和验收标准；不在设计阶段顺手重构代码。

### 判断一项设计是否成功，先看这些问题

- 用户打开首页后，能否在很短时间内判断应该进入哪个工程？
- 进入工程后，能否快速找到当前要推进的 Task 和下一步？
- 做完一段工作后，能否自然地记录实际进展，而不必面对一整块长表单？
- 常用操作是否直观，低频操作是否不会一直抢注意力？
- 个人工程是否拥有完整、自然的创建和进入路径？
- 团队能力是否依然存在，却不迫使个人用户理解团队概念？

请优先用真实工作路径判断设计，而不是用“看起来更现代、更简洁、更高级”判断。

### 产品立场：个人工程管理系统，而不是 Workspace 管理系统

Mini Plane 的首要用户是**一个人管理多个持续推进的工程**。其常见使用循环是：

> 打开软件 → 扫一眼所有工程的进展 → 选择要继续的工程 → 查看 NOW/NEXT → 推进 Task → 记录 Worklog → 离开或切换到另一个工程。

个人的主任务是推进自己正在做的工程，而不是管理组织、成员与角色。

因此：

- **My Engineering 是个人首页与产品主入口**，不应再被 Workspace Dashboard 的思路影响。
- Project 的存在不应以 Workspace 为前提。创建个人工程应是自然的默认流程。
- Workspace、成员、角色、协作设置等能力继续保留，但放在清楚的“团队协作”区域或按需入口中。
- 个人工程和团队工程可以在个人总览中清楚地区分，但不能让团队身份、成员数、角色徽章成为每张工程卡片的主要内容。
- 不要为了“支持协作”而把个人使用的主流程设计成先选工作区、再找项目、再进入任务的层层导航。
- Engineering Island 应是多个工程的轻量实时状态投影，不应该成为另一套完整的项目管理后台。

## 三、个人用户的信息优先级

设计每一屏时都请按以下层级思考；具体排版可比较、可质疑，但不能把低频的团队管理与高频的工程推进放在同一优先级。

### P0：日常高频——首屏必须支持

- 我有哪些正在推进的工程？
- 哪些工程最近有进展，哪些可能停滞或受阻？
- 每个工程的当前阶段、NOW、NEXT 是什么？
- 最近一次实际工作记录是什么？
- Agent 是否正在运行？其状态是否真实、可信？
- 如何进入工程并快速推进一个任务？
- 如何快速记录本次实际完成的工作？

### P1：周期性操作——应该容易找到，但不必全部常驻

- 查看和调整完整 Stage 路线；
- 查看任务历史、组合筛选、排序和批量操作；
- 查阅 Worklog 的详细结论、阻塞、下一步；
- 查看 Task 的评论、活动与关联信息；
- 调整计划和工程设置。

### P2：低频管理——不应主导个人主界面

- 创建/管理 Workspace；
- 成员邀请、角色和协作权限；
- 复杂的协作设置；
- UUID、审计元信息等不常查看的内容；
- 不属于当前工作目标的管理型操作。

**重要：降低优先级不等于删除功能。** 高级能力应保留，通过清晰的入口、编辑态、二级面板或团队协作区域承载。

## 四、现有设计应该保留什么、重新思考什么

### 应保留的品牌资产

- 暖纸色底、克制的钴蓝、细线、网格和留白；
- Cormorant Garamond 与 Inter 的排版组合；
- 工程图纸与编辑刊物融合的 Blueprint Editorial 气质；
- Task / Worklog / Stage / NOW / NEXT / Agent 这些体现产品理念的核心内容；
- 直角构图、轻量控件、无厚重阴影的界面性格。

### 可以且应该重新评估的旧规则

- 每个信息区是否都必须常驻在同一个页面；
- 是否应该让阶段路线、日志表单、筛选栏、任务列表同时展开；
- 所有页面是否都必须同等强调个人入口和团队入口；
- 所有内容区域是否都要显示同等强度的网格；
- 装饰性英文、微标签、坐标标注是否已经超过实际信息的可读性；
- 项目卡片是否对只有 1 个工程和拥有 10 个工程的情况都合适；
- 一个页面为了“一屏读完”是否塞入了过多不同工作模式。

不能为了保留历史设计规则而牺牲实际操作体验。反过来，也不能因为想简洁，就把它改成普通的圆角卡片式 SaaS 模板。

## 五、请重点解决的 6 个设计问题

以下是从 README 真实截图中观察到的问题假设，请结合实际情况验证，不需要机械照单全收。

### 1. 个人首页：从“浏览卡片”升级为“选择下一步工作”

目前首页有今日统计和工程卡片，视觉统一，但需要进一步思考：它是否帮助用户决定接下来做什么？仅展示工程数量、百分比和 NOW/NEXT 文字，不一定能充分支持“我今天先继续哪个工程”的判断。

请研究：

- 是否需要在页面上区分“正在推进”“最近活动”“暂时搁置”等状态？只有存在可靠数据依据时才显示，不要凭空推断项目已停滞或阻塞。
- NOW、NEXT、最近 Worklog、Agent 状态各自应该展示多少内容？哪些应优先？
- 首页主操作是“继续工程”“快速记录进展”还是“新建工程”？请根据用户场景取舍，不要把所有动作都做成同等显眼的按钮。
- 工程卡片/行如何适应 1、3、8 个工程？请使用真实数据和不同数量做对照。
- 有个人工程、团队工程混在一起时，如何以个人工作为主、又不隐藏协作来源？
- 空状态应直接提供“创建个人工程”，不能只提示创建 Workspace。

首页应让用户更容易做出下一步决定，而不只是展示统计数据。

### 2. 主导航：个人空间是默认路径，团队协作是按需进入

请重新设计信息架构，不要只修改目前顶栏的切换按钮。

需要回答：

- 一级导航中什么是个人高频入口？什么属于协作入口？
- “我的工程”“工程内任务”“计划”“进展记录”“设置”“团队协作”之间是什么关系？
- 用户如何清楚地区分个人工程与团队协作工程？
- 从团队工程返回个人首页是否直观？用户是否会丢失原来的任务筛选、抽屉和页面上下文？
- 顶栏与左侧栏是否存在重复入口？哪些入口可合并？

请提出两种不同的导航结构并比较。不要为了看起来完整，给所有功能都设置同等醒目的一级导航。

### 3. 工程主页：核心是推进工作，不是同时编辑所有模块

现有项目页把 Stage 路线编辑、Worklog 录入、状态筛选、优先级、标签、负责人、排序与 Task 列表连续铺开。请从个人日常工作流程出发重新组织。

重点探讨：

- 首屏是否优先展示工程名称、当前阶段、NOW/NEXT、最近实际进展与 Agent 状态？
- Task 列表是不是主要工作区？如果是，是否应该减少它上方常驻的编辑表单？
- Stage 默认应以清晰的只读路线呈现，还是作为独立计划视图？完整编辑何时出现？
- Worklog 是否改为一个随时可达的“记录进展”入口，打开轻量快速记录；需要时再补全结论、下一步、阻塞和阶段关联？
- 工程概览、任务、计划与日志应该同屏分区、可折叠，还是拆成少数清楚的视图？请用实际操作频率论证，而不要预设“所有内容必须单页”或“每类功能必须一页”。

核心标准：**进入工程后，不需要先处理计划设置或表单，就能找到并推进当前任务。**

### 4. Worklog：让“记下刚才做了什么”成为自然动作

Task 是计划，Worklog 是实际证据，两者不能合并。请重点比较：

- 常驻完整表单；
- 轻量快速记录入口，默认只输入标题/本次完成内容；
- 快速记录后，可选补全结论、下一步、阻塞、日期与关联 Stage；
- 在工程页内打开的侧边面板/抽屉。

请明确哪种方案最符合个人高频记录；怎样避免用户为了写一条日志被大量字段阻挡；怎样保留编辑历史日志的能力；怎样防止未提交输入因切换视图而丢失。

不要为了追求“表单短”而丢掉 Worklog 的关键字段，也不要把“快速记录”和“完整编辑”做成两套语义不一致的数据流程。

### 5. Task 筛选与详情：常用动作快，复杂操作不消失

任务列表当前可筛选状态、优先级、标签、负责人、排序和搜索；Task Drawer 还包含描述、元信息、活动、评论、关联和删除。

请研究：

- 常用状态入口是否直接可见？搜索是否容易触达？
- 优先级、标签、负责人等是否能合并为一个“筛选”入口，同时展示已选条件摘要与“清除筛选”？
- 当前筛选条件是否需要常驻在 URL，返回列表时是否保留？（产品行为原则不应因视觉重构丢失。）
- Task Drawer 中状态、优先级、负责人等常用字段放在哪里最自然？
- 评论和活动是否应该同屏，还是使用清晰切换？
- UUID、创建/更新时间、危险操作等低频内容如何收纳？
- 如何避免一个任务详情页出现多组同等突出的按钮？

不要为了减少按钮把所有功能塞进深层菜单。要求在“容易发现”和“不过度干扰”之间取得明确平衡。

### 6. Engineering Island：主应用的状态摘要，而非另一份后台

Island 本轮不是第一优先级。请先让主应用的工作流程成立，再讨论它与主应用的分工。

- Island 优先回答：工程当前状态、NOW、STEP/HOW、NEXT、DONE、Agent 运行态。
- 不要在 Island 中重复构建完整的任务筛选、复杂计划编辑或团队管理。
- 让用户能自然返回主应用的对应工程，避免重复导航。
- 保留单窗两态的既有窗口模型；不要未经论证重做桌面窗口行为。
- 如果当前主应用的信息结构尚未稳定，只需说明 Island 后续如何适配，不要先花大量时间重做它。

## 六、必须交付真正不同的设计方案，而不是换颜色

为避免只更换配色、字体或圆角，本轮必须先决定信息架构与操作流程，再调整视觉细节。

### 交付 1：5–8 个根本问题

用表格说明每个问题的具体证据、影响的个人用户场景、出现频率、建议方向和代价。区分截图可以直接确认的事实与需要原型验证的假设。不要输出几十条零碎 CSS 建议。

### 交付 2：个人用户关键流程图

至少绘制以下流程的现状与建议版本：

1. 打开软件 → 找到今天要继续的工程；
2. 创建个人工程 → 开始推进第一个任务；
3. 进入工程 → 找到 NOW → 修改/完成 Task；
4. 完成工作 → 快速记录 Worklog；
5. 需要时调整 Stage 计划；
6. 查阅 Task 详情、评论和活动；
7. 需要团队协作时进入团队能力，再返回个人工程。

每条流程注明主要操作次数、重复输入、滚动、页面跳转、弹层打开，以及用户必须理解的概念数量。不要为了追求点击次数少而把所有操作挤成复杂菜单。

### 交付 3：至少两种不同的个人版信息架构

例如但不限于：

- **方案 A：工程总览 + 工程工作台。** 个人首页聚合所有工程；进入单个工程后，以 NOW/NEXT 和 Task 推进为主，计划与日志按需展开。
- **方案 B：个人工作流优先。** 首页更强调“继续上次的工作/当前待推进事项/最近记录”，工程列表作为另一个入口；进入工程后按任务推进、记录进展与阶段计划组织。

这只是供比较的方向，不是预定答案。请结合现有能力提出最适合 Mini Plane 的方案，说明是否有必要融合二者。团队协作应该作为清晰但次级的路径，而不是与个人主路径平分注意力。

### 交付 4：核心屏幕 A/B 线框对照

至少做以下屏幕的结构对照：

1. **My Engineering 首页**：空状态、1 个工程、多个工程；
2. **个人工程主页**：工程状态、NOW/NEXT、Task、Plan、Worklog 的层级关系；
3. **Worklog 快速记录**：快速记录与完整编辑的关系；
4. **Task Drawer**：常用编辑、描述、评论/活动、元信息、危险操作；
5. **个人/团队切换与团队入口**：不打断个人使用，又能保留完整协作能力。

A/B 应体现结构、内容优先级或操作流程的真实差异，不能只是换背景色。请用相同内容、相同窗口尺寸作比较。可用文本线框图、Markdown 图、低保真原型或独立静态 HTML。

如果制作 HTML 原型，将其放到独立设计探索目录或临时分支；不要接生产路由，不要修改已有业务逻辑，不要引入新的 UI 库。

### 交付 5：推荐方案和明确取舍

推荐一个主方案，可以吸收另一个方案的优点。必须回答：

- 为什么它最适合“一个人管理多个持续推进的工程”；
- 打开软件后用户第一眼看到什么，为什么；
- 哪些操作留在首屏、哪些进入按需展开区；
- 个人工程如何创建、进入、继续推进；
- 团队能力在什么位置出现，为什么不会干扰个人；
- 哪些旧设计应该保留，哪些规则应修改；
- 有哪些代价或风险，例如页面切换增加、功能发现性下降、低频入口太深等。

### 交付 6：设计规范与实施映射

输出清晰的导航结构、主要页面层级、按钮优先级、筛选交互、Worklog 交互、Stage 编辑模式、Task Drawer 结构、空状态、错误状态与键盘行为。说明哪些现有组件可复用、哪些组件可能需要调整、哪些能力需要后续确认 API/路由支持。

本轮仅记录实现依赖，不做全仓库审计。不要擅自新增复杂架构、状态管理库、图表库或大量抽象组件。

### 交付 7：最小验证原型和分期计划

先选最能验证个人体验的 1–2 个场景。建议候选：

- My Engineering 首页：用户如何选出接下来要继续的工程；
- 工程主页：用户如何找到 NOW、推进任务并快速记录一次 Worklog。

## 七、视觉与交互约束

### 视觉要求

- 保留暖纸色、衬线标题、钴蓝强调、细线与蓝图编辑风格；
- 可以调整网格在主要内容区的强度，保证列表、表单和正文阅读优先；
- 操作文字、表格正文、中文提示要清晰可读，不得为了所谓精致缩小到难以辨认；
- 按钮主次要明确，主操作不应被十几个低频控件淹没；
- 不要引入常见 SaaS 模板风格：大面积圆角卡片、渐变、毛玻璃、霓虹、堆叠阴影；
- 不要用装饰性英文和微标签替代清楚的功能名称。

### 交互要求

- 个人工程创建是直接路径，不应要求先创建 Workspace；
- 个人首页和工程页面应该提供明确的“下一步”，但不要凭空推断任务优先级、阻塞或 Agent 状态；
- 快速记录不能破坏 Worklog 的完整语义与数据；
- 筛选、抽屉与列表之间的返回行为应可预测，已选筛选条件不应无故丢失；
- 高级筛选、阶段编辑、批量操作、评论/活动、协作成员功能可以收纳，但仍需可发现；
- 删除等危险操作与普通编辑明确分离；
- 桌面 Island 继续遵守已有单窗两态壳层模型，除非拿出明确证据说明需要调整。
